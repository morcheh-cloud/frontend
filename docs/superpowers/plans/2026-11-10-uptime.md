# Uptime — پلن فیچر

> تاریخ: 2026-11-10 · وضعیت: پیش‌نویس، منتظر تصمیم‌های بخش آخر
> هدف: مانیتورینگ در دسترس بودن (availability) هر چیزی که تیم دارد — وب، سوکت، دیتابیس، صف، ایمیل، سرویس‌های داخلی — کامل‌تر از Uptime Kuma و یکپارچه با بقیه‌ی مورچه.

---

## ۱. جایگاه در محصول

- بخش جدید **Uptime** در گروه Observability منو (`/uptime`). جای‌خالی فعلی `/monitoring/uptime` حذف یا به آن redirect می‌شود.
- **اعلان‌ها (Notifications)** یک ماژول مشترک جدا است که جای‌خالی فعلی `/alerts` (Rules / Channels) را واقعی می‌کند. Uptime اولین مصرف‌کننده‌اش است، ولی بعداً سرور down، بکاپ ناموفق، cron job خراب، گواهی رو به انقضا و… هم از همین کانال‌ها خبر می‌دهند.
- نام در کد: `monitor` (جدول‌ها، API، کامپوننت‌ها)، نام در UI: Uptime / Monitor.

## ۲. چرا از Uptime Kuma بهتر است

| موضوع | Uptime Kuma | مورچه |
|---|---|---|
| کاربران و دسترسی | تک‌کاربره | workspace + سطح‌های Viewer…Owner که الان داریم |
| محل بررسی | فقط از خود سرور Kuma | از مورچه **و از هر سروری که SSH دارد** (probe بدون نصب agent) — شبکه‌ی داخلی، دیتاسنترهای مختلف، داخل/خارج ایران |
| تصمیم down | یک نقطه | اجماع چند location (مثلاً ۲ از ۳) → false alarm کمتر |
| وابستگی‌ها | ندارد | گراف وابستگی: سرور down ⇒ مانیتورهای وابسته «متأثر» علامت می‌خورند و جدا alert نمی‌دهند (root cause) |
| Incident | فقط event | Incident واقعی: Acknowledge، یادداشت، timeline، مسئول، Resolve، post-mortem |
| Escalation / on-call | ندارد | سیاست escalation (اگر X دقیقه ack نشد → نفر بعد)، ساعت سکوت، on-call (فاز آخر) |
| SLO / گزارش | درصد uptime | SLA هدف، error budget، MTTR/MTBF، percentile زمان پاسخ به تفکیک location، گزارش ماهانه CSV/PDF |
| ساخت مانیتور | دستی | پیشنهاد خودکار از دارایی‌های موجود: سایت‌های proxy، Services، دیتابیس‌ها، storage، DNS، پورت‌های باز سرور، cron jobها |
| Status page | دارد | + دامنه‌ی اختصاصی با یک کلیک (از طریق Reverse proxy + گواهی)، RTL/فارسی، subscriber، incident update |
| اسکریپت سفارشی | ندارد | اجرای plugin‌های Nagios/Icinga روی هر سرور از طریق SSH (exit code 0/1/2/3 + perfdata) |
| as-code | ندارد | export/import YAML، API token، endpoint `/metrics` برای Prometheus |
| مهاجرت | — | Import از backup JSON کوما |

## ۳. انواع مانیتور

هر نوع = یک `Checker` در بک‌اند با فرم مخصوص خودش در UI. ستون «فاز» ترتیب ساخت است.

### ۳.۱ وب و API

| نوع | چه چیزی بررسی می‌شود | فاز |
|---|---|---|
| **HTTP(S)** | method، headers، body، auth (Basic / Bearer / Digest / mTLS)، کدهای وضعیت قابل‌قبول، follow redirect، HTTP/1.1/2/3، IPv4/IPv6 اجباری، proxy خروجی | 1 |
| Assertionها روی HTTP | keyword / regex (وجود یا عدم وجود)، JSONPath (`$.status == "ok"`)، header، اندازه‌ی body، زمان پاسخ بیش از X ⇒ **Degraded** | 1 |
| **TLS certificate** | انقضا (هشدار ۳۰/۱۴/۷ روز قبل)، زنجیره، hostname، TLS نسخه، OCSP — روی هر پورت، با STARTTLS برای SMTP/IMAP/POP3/FTP/Postgres | 1 |
| **Domain expiry** | RDAP/WHOIS (شامل `.ir` از طریق whois.nic.ir) | 2 |
| **WebSocket** | handshake، subprotocol، ارسال پیام و انتظار پاسخ (keyword/JSON)، ping/pong، زمان تا اولین پیام | 2 |
| Socket.IO | اتصال namespace، emit و انتظار event | 2 |
| SSE | اتصال و دریافت حداقل یک event در زمان مشخص | 2 |

| **Multi-step API** | زنجیره‌ی درخواست‌ها با متغیر (login → گرفتن token → فراخوانی API)، هر قدم assertion خودش | 4 |
| Browser synthetic | Playwright headless: باز کردن صفحه، کلیک، پر کردن فرم، screenshot در خطا | 4 |

### ۳.۳ دیتابیس‌ها

حالت ساده: اتصال + `SELECT 1` (یا معادل). حالت پیشرفته: **query دلخواه + شرط** روی مقدار/تعداد سطر (مثلاً «تعداد jobهای pending < 1000»). دیتابیس‌هایی که الان در `/databases` ثبت شده‌اند با یک کلیک مانیتور می‌شوند (همان credential، همان تونل SSH).

| فاز ۲ (درایور Go را داریم) | فاز ۳ |
|---|---|
| PostgreSQL (و CockroachDB، TimescaleDB، Supabase) | ClickHouse |
| MySQL / MariaDB (و TiDB، PlanetScale) | Elasticsearch / OpenSearch (cluster health: green/yellow/red) |
| SQL Server | Cassandra / ScyllaDB |
| MongoDB (و replica set: primary دارد؟) | InfluxDB، etcd، Consul |
| Redis / Valkey / KeyDB / Dragonfly (+ Sentinel، Cluster state) | Memcached، ZooKeeper (`ruok`/`mntr`)، Neo4j، CouchDB، Oracle |

| **Kafka** | اتصال به brokerها، وجود topic، **consumer group lag** با آستانه، تعداد partition‌های under-replicated | 2 |

### ۳.۷ Push / Heartbeat (dead-man's switch)

- هر مانیتور push یک URL مخفی دارد (`/push/<token>`)؛ اگر در «بازه + grace» صدا زده نشود ⇒ Down.
- سیگنال‌های `start` / `success` / `fail` (مثل healthchecks.io) ⇒ **مدت اجرا** ثبت می‌شود و «طولانی‌تر از X» هم alert می‌دهد.
- بازه می‌تواند cron expression با timezone باشد (برای jobهای شبانه).
- body درخواست (تا ۱۰ KB، مثلاً خروجی اسکریپت) در event ذخیره می‌شود.
- **یکپارچگی:** cron jobهای مورچه و cron جدول سرورها دکمه‌ی «Monitor this» دارند که خط `curl` را به دستور اضافه می‌کند.

### ۳.۸ مانیتورهای ترکیبی

- **Group**: وضعیت از روی فرزندان (همه / هرکدام / N از M) — برای «سرویس پرداخت» = API + DB + صف.
- **Dependency**: «این مانیتور به X وابسته است»؛ وقتی X down است، این‌ها «Affected» می‌شوند نه Down و alert جدا نمی‌دهند. وابستگی خودکار: مانیتوری که روی سرور S اجرا می‌شود یا به آدرس S می‌رود به مانیتور سرور S وابسته است.

## ۴. موتور بررسی

### ۴.۱ وضعیت‌ها

`Up` · `Degraded` (کند یا assertion نرم) · `Down` · `Pending` (در حال retry قبل از اعلام Down) · `Paused` · `Maintenance` · `Affected` (وابستگی down است) · `Unknown` (probe قابل اجرا نیست، مثلاً SSH قطع)

### ۴.۲ تنظیمات هر مانیتور

- بازه (حداقل ۱۰ ثانیه، پیش‌فرض ۶۰)، timeout، **retry قبل از Down** (پیش‌فرض ۲)، بازه‌ی retry جدا، **Up شدن پس از N موفقیت** (ضد flap)
- آستانه‌ی Degraded برای زمان پاسخ؛ تشخیص flapping (اگر در ۱۵ دقیقه بیش از K تغییر ⇒ یک incident «ناپایدار» به جای ده alert)
- tagها، پوشه/گروه، یادداشت markdown، لینک به runbook، مسئول (owner)، اهمیت (Critical / Normal / Low)
- آرشیو تاریخچه وقتی مانیتور حذف می‌شود (اختیاری)

### ۴.۳ Location و probe

- **Morcheh** (خود backend) — همیشه در دسترس.
- **هر سرور پنل به‌عنوان probe**، بدون نصب چیزی:
  - چک‌های مبتنی بر TCP (HTTP، WebSocket، DB، صف، SMTP…) کد Go را در مورچه اجرا می‌کنند ولی اتصال از طریق کانال `direct-tcpip` همان SSH می‌رود (همان روشی که مانیتور دیتابیس الان استفاده می‌کند) ⇒ اتصال واقعاً از شبکه‌ی آن سرور شروع می‌شود.
  - ICMP/UDP/DNS/traceroute با اجرای `ping`/`dig`/`mtr` روی سرور (اگر نصب نیست، notice + دکمه‌ی نصب).
- قانون تصمیم: `any` / `majority` / `all` / «حداقل N location» ⇒ Down. نمودار و uptime به تفکیک location.
- هر location ساعت و منطقه‌ی خودش را نشان می‌دهد (مثلاً «تهران — Asiatech»، «آلمان — Hetzner»).

### ۴.۴ زمان‌بندی و مقیاس

- Scheduler با jitter (همه‌ی مانیتورها هم‌زمان نزنند)، worker pool با سقف هم‌زمانی کلی و per-host (به یک سرور بیش از N چک هم‌زمان نزنیم).
- هدف: ۲۰۰۰ مانیتور با بازه‌ی ۳۰ ثانیه روی یک instance.
- Leader election ساده با Postgres advisory lock (اگر بعداً چند replica از backend داشتیم).

### ۴.۵ ذخیره‌سازی داده

- `monitor_checks`: هر نتیجه (زمان، location، وضعیت، latency، کد، پیام خطا، timing breakdown: DNS/connect/TLS/TTFB/total) — نگهداری خام ۱۴ روز (قابل تنظیم).
- `monitor_rollups`: تجمیع دقیقه‌ای → ساعتی → روزانه (تعداد، موفق، min/avg/p50/p95/p99) — ساعتی ۹۰ روز، روزانه ۲ سال.
- Partition ماهانه روی `monitor_checks` تا حذف داده‌ی قدیمی ارزان باشد.
- فقط **تغییر وضعیت‌ها** (`monitor_events`) برای همیشه نگه داشته می‌شوند.

## ۵. Incident و اعلان

### ۵.۱ Incident

- Down شدن یک مانیتور (یا گروه) ⇒ incident باز می‌شود؛ مانیتورهای Affected زیر همان incident جمع می‌شوند.
- چرخه: `Open → Acknowledged → Resolved` (+ Resolve خودکار با Up شدن، قابل خاموش کردن).
- Timeline: تغییرات وضعیت، alertهای ارسال‌شده، ack، یادداشت‌های تیم، خروجی traceroute و پاسخ HTTP لحظه‌ی خطا (body تا ۶۴ KB، headers)، screenshot در browser check.
- Post-mortem markdown و «انتشار روی status page».
- اقدام خودکار اختیاری (فاز ۴): وقتی Down شد ⇒ restart سرویس systemd/container، یا اجرای یک Script/Ansible playbook موجود. (با سطح دسترسی ذخیره‌کننده، مثل cron jobها.)

### ۵.۲ کانال‌ها (`/alerts/channels`، ماژول مشترک `internal/notify`)

| فاز ۱ | فاز ۲ | فاز ۳ |
|---|---|---|
| Email (SMTP) | Slack، Discord، Mattermost، Rocket.Chat | PagerDuty، Opsgenie، Grafana OnCall |
| **Telegram** | Microsoft Teams، Google Chat | Signal (signal-cli REST)، Matrix |
| **Bale** (bot API) | ntfy، Gotify، Pushover | تماس صوتی (Kavenegar)، Twilio SMS/Voice |
| Webhook (template JSON دلخواه، امضای HMAC) | SMS ایرانی: Kavenegar، SMS.ir، Melipayamak، Ghasedak | Web Push در مرورگر/موبایل |

- هر کانال: دکمه‌ی **Send test**، قالب پیام قابل ویرایش (متغیرها: `{{monitor.name}}`، `{{status}}`، `{{reason}}`، `{{duration}}`، `{{link}}`)، زبان پیام فارسی/انگلیسی.
- Secretها رمزنگاری‌شده مثل بقیه‌ی credentialها؛ Owner workspace یا admin مدیریت می‌کند.

### ۵.۳ قوانین (`/alerts/rules`)

- مسیریابی: بر اساس tag / workspace / اهمیت / نوع رویداد (Down، Degraded، Recovered، cert expiring، flapping).
- **Escalation policy**: مرحله‌ها با تأخیر (۰ دقیقه → تلگرام تیم، ۱۰ دقیقه بدون ack → SMS مسئول، ۳۰ دقیقه → تماس مدیر).
- یادآوری دوره‌ای تا وقتی Down است (مثلاً هر ۳۰ دقیقه)، ساعت سکوت (فقط Critical)، throttle و dedup.
- خلاصه‌ی روزانه/هفتگی (digest).
- **On-call schedule** با چرخش هفتگی و جایگزینی (فاز ۴).
- Ack از داخل پیام: لینک امضاشده در ایمیل/تلگرام/بله (دکمه‌ی inline در بات).

## ۶. Maintenance windows

- یک‌باره یا تکراری (cron + timezone)، برای مانیتور / tag / سرور / کل workspace.
- در این بازه: چک ادامه دارد ولی alert نمی‌رود و در uptime/SLA حساب نمی‌شود (قابل تنظیم).
- **خودکار:** Reboot/Shutdown از منوی Power، نصب/آپدیت از Applications، اجرای Ansible روی سرور ⇒ maintenance موقت روی مانیتورهای آن سرور تا برگشتن.
- روی status page اطلاع‌رسانی از قبل.

## ۷. Status page

- چند صفحه برای هر workspace؛ عمومی، با رمز، یا فقط IPهای مجاز.
- آدرس: `/<slug>` روی دامنه‌ی مورچه یا **دامنه‌ی اختصاصی**: با یک کلیک یک proxy host روی Reverse proxy ساخته می‌شود + گواهی Let's Encrypt.
- ظاهر: لوگو و رنگ (از workspace look)، تم روشن/تیره، **فارسی/انگلیسی با RTL**، CSS دلخواه، footer.
- محتوا: گروه‌های کامپوننت (هر کدام یک یا چند مانیتور با نام عمومی متفاوت از نام داخلی)، نوار ۹۰ روزه، نمودار زمان پاسخ اختیاری، incidentهای جاری با updateها (Investigating → Identified → Monitoring → Resolved)، maintenanceهای آینده، تاریخچه.
- Subscribe: ایمیل، webhook، RSS/Atom، (فاز ۳) Telegram/Bale.
- Badge SVG برای README: وضعیت، uptime ۷/۳۰ روز، زمان پاسخ، انقضای گواهی.
- JSON API عمومی (سازگار با فرمت Atlassian Statuspage برای ابزارهای موجود).
- صفحه‌ی سبک بدون JS سنگین، cache‌شده (رندر سمت سرور در backend یا یک route جدای Next؛ پنل خودش SSR ندارد).

## ۸. گزارش و SLO

- هدف SLA برای هر مانیتور/گروه (مثلاً 99.9%) ⇒ error budget باقی‌مانده و نرخ مصرف (burn rate) با هشدار.
- uptime ۲۴h/۷d/۳۰d/۹۰d/۱y، MTTR، MTBF، تعداد incident، percentile زمان پاسخ به تفکیک location و مرحله (DNS/connect/TLS/TTFB).
- گزارش ماهانه قابل دانلود CSV/PDF و ارسال خودکار ایمیلی.
- تب Insights با همان ماژول مشترک `src/components/insights/`.

| `/uptime/status-pages/[id]` | ویرایشگر با **پیش‌نمایش زنده** کنار فرم (desktop) |
| `/alerts/channels`، `/alerts/rules` | کانال‌ها و قوانین (ماژول مشترک) |
| تب سرور `/servers/[id]/uptime` | مانیتورهایی که روی این سرور هستند یا از آن probe می‌شوند (گروه Monitoring) |

### یکپارچگی با بقیه‌ی پنل

- دکمه‌ی **«Monitor this»** در: سایت‌های Reverse proxy، Services launcher، دیتابیس، Storage، DNS zone، ردیف Ports، cron job (push)، systemd service.
- **پیشنهاد خودکار** در خالی بودن صفحه: «۱۲ سایت proxy و ۴ دیتابیس مانیتور نشده‌اند — همه را اضافه کن» (با پیش‌نمایش و تیک).
- Home: tally + issues؛ عدد قرمز منو (`useNavAlerts`)؛ palette: `New monitor`، جستجوی مانیتورها؛ intent `add-monitor`.
- بروزرسانی زنده با SSE (`/monitors/stream`)، مثل jobs.
- موبایل: لیست native با نوار heartbeat، sheetها، Ack از روی notification push.
- راهنما: guide `uptime` (+ `alerts`) با مثال‌ها، تنظیمات پیشنهادی و troubleshooting.

## ۱۰. دسترسی‌ها

| سطح workspace | مجوز |
|---|---|
| Viewer | دیدن مانیتورها، نمودارها، incidentها |
| Operator | Check now، Pause/Resume، Ack، یادداشت incident، maintenance |
| Engineer | ساخت/ویرایش مانیتور، status page خصوصی |
| Owner | حذف، کانال‌ها و قوانین اعلان، status page عمومی/دامنه، اقدام خودکار |

- استفاده از یک سرور به‌عنوان probe = Operator روی آن سرور؛ چک‌هایی که روی سرور دستور اجرا می‌کنند (Docker، systemd، plugin) = Engineer.
- مانیتور با دسترسی آخرین ذخیره‌کننده اجرا می‌شود (مثل cron jobها) و هنگام اجرا دوباره چک می‌شود.

## ۱۱. معماری بک‌اند (خلاصه)

- `internal/uptime/`: interface `Checker { Check(ctx, Target, Dialer) Result }`، یک فایل برای هر نوع؛ `Dialer` = مستقیم یا از طریق `sshpool`.
- `internal/uptime/scheduler.go`، `evaluate.go` (retry، اجماع location، flap، dependency)، `rollup.go`.
- `internal/notify/`: driver هر کانال + قالب‌ها + escalation queue.
- جدول‌ها: `monitors`، `monitor_locations`، `monitor_checks` (partitioned)، `monitor_rollups`، `monitor_events`، `incidents`، `incident_updates`، `maintenances`، `status_pages`، `status_page_components`، `status_subscribers`، `notification_channels`، `notification_rules`، `escalation_policies`، `push_tokens`.
- API: CRUD مانیتورها، `POST /monitors/test` (بدون ذخیره)، `POST /monitors/{id}/check`، `GET /monitors/{id}/checks?range`، `GET /monitors/stream` (SSE)، incidents، maintenances، status pages، `GET|POST /push/{token}` (public، rate-limited)، `GET /status/{slug}` (public)، `GET /badge/{id}/{kind}.svg`، `GET /metrics` (Prometheus، با token)، export/import YAML.
- همه‌ی endpointها در `policies` با سطح مناسب.

## ۱۳. تصمیم‌های باز

1. **مسیر منو:** `/uptime` مستقل در Observability (پیشنهاد) یا همان `/monitoring/uptime`؟ (جای‌خالی‌های Monitoring/Metrics/Logs فعلاً ساخته نشده‌اند.)

3. **حداقل بازه:** ۱۰ ثانیه یا ۲۰ ثانیه؟ (بار روی سرورهای probe)

5. **Browser synthetic** (Playwright) کانتینر جدا لازم دارد — در deploy compose اضافه شود یا اختیاری بماند؟
